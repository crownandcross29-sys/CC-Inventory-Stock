## 1. Project Summary

You're building a two-part system:

1. **CC-Inventory-Stock** — a private admin app where you manage products (add/edit/delete, stock status). It outputs a JSON file that acts as your "database."
2. **CC-Hosting-Public** — the public storefront, nested as a sub-repo inside repo 1, which reads that JSON and renders the live site. This is what gets deployed on Vercel.

Everything else (cart, payments, policies, marketing) sits inside the public repo as pages/features.

This is a lean, no-backend-database architecture — good for getting to market fast and free-tier friendly, but it has real limits you should know about upfront (see Section 8).

## 2. Recommended Tech Stack

| Layer | Recommendation | Why |
|---|---|---|
| Framework | **Next.js** (React) | File-based routing, works great on Vercel, handles both static pages and API routes, responsive by default |
| Styling | **Tailwind CSS** | Fast to build responsive (small/medium/large screen) layouts |
| Hosting | **Vercel** | Free tier, auto-deploys from GitHub, exactly what you specified |
| Version control | **GitHub** | Two repos as you outlined, or repo + submodule |
| Data store | **JSON file** (`products.json`) generated by Repo 1 | Matches your spec; upgrade path noted below |
| Images | **Google Drive / Google Photos share links**, or Vercel/Cloudinary | You specified "Google images + link option" — works, with caveats (Section 8) |
| Cart → Order | **WhatsApp deep link** (`wa.me`) or **mailto:** link with pre-filled order text | No backend needed |
| Payment | **UPI Deep Link + auto-generated QR** | `upi://pay?...` URI, rendered as QR client-side |
| Local dev launcher | Shell/batch scripts (`start.sh`, `start.bat`) or a small Node CLI | Cross-platform local hosting |

## 3. Repository Architecture

```
CC-Inventory-Stock/                 (Repo 1 — private, admin only)
├── admin/                          Admin UI (product CRUD)
│   ├── pages/ or app/
│   ├── components/
│   └── lib/generateJson.js         Builds/updates products.json
├── CC-Hosting-Public/               (Repo 2 — nested as git submodule)
│   ├── ...                          (full Next.js storefront, see below)
│   └── public/data/products.json    <-- Repo 1 writes here
├── scripts/
│   ├── start.sh                    Mac/Linux launcher
│   ├── start.bat                   Windows launcher
│   └── start.js                    Cross-platform Node launcher (recommended)
└── README.md
```

> **Dependency install rule:** All dependency / env folders are installed **co-located in the same dir as their project** (e.g. `admin/node_modules/`, `CC-Hosting-Public/node_modules/`, `admin/.venv/`), never at the repo root. Every generated folder below is gitignored (see `.gitignore`).

**How the JSON hand-off works:**
- Repo 1 (admin) is where you add/edit products.
- On save, Repo 1 writes/updates `CC-Hosting-Public/public/data/products.json`.
- Since Repo 2 is a **git submodule**, you commit inside Repo 2, push Repo 2, then update the submodule pointer in Repo 1.
- Vercel is connected to **Repo 2 only** — every push to Repo 2's main branch triggers a redeploy.

**Why a submodule (not just a folder)?**
- Keeps the public site's git history clean and independent.
- Lets you keep Repo 1 (admin, possibly containing sensitive logic) private while Repo 2 stays deployable/public.
- Vercel only ever sees Repo 2, so your admin code never ships to the storefront bundle.

**Alternative if submodules feel fiddly:** use a GitHub Action in Repo 1 that, on product save/commit, pushes the updated `products.json` directly to Repo 2 via the GitHub API. Slightly more setup, but removes the manual "update submodule pointer" step. Worth doing once you're past MVP.

## 4. Local Launcher (Windows / Mac / Linux)

A single Node.js script is the most reliable cross-platform option (avoids maintaining separate `.sh` and `.bat` files):

```js
// scripts/start.js
const { spawn } = require("child_process");
const isWin = process.platform === "win32";

function run(cmd, args, cwd) {
  spawn(isWin ? `${cmd}.cmd` : cmd, args, { cwd, stdio: "inherit", shell: isWin });
}

run("npm", ["run", "dev"], "./admin");              // Admin on :3000
run("npm", ["run", "dev", "--", "-p", "3001"], "./CC-Hosting-Public"); // Storefront on :3001
```

Run with `node scripts/start.js` on any OS. Add a matching `npm run launch` script in `package.json` so it's a one-liner regardless of platform.

## 6. Key Feature Notes

### Cart → WhatsApp / Email handoff
No backend order processing needed for MVP:
```
https://wa.me/91XXXXXXXXXX?text=New%20Order%3A%20Jersey%20-%20Messi%20Argentina%20Retro%2C%20Size%20L%2C%20Qty%201
```
Build this string client-side from cart state, open on click. Same idea with `mailto:`.

### UPI QR Auto-Generation
UPI deep link format:
```
upi://pay?pa=yourupi@bank&pn=CrownAndCross&am=1499&tn=Order%23CC1023&cu=INR
```
Generate a QR from this string client-side (e.g., `qrcode.react` or `qrcode` npm package) — no payment gateway account needed for a basic "scan and pay" flow. **Caveat:** this does not auto-confirm payment; you'll need a manual reconciliation step (customer sends screenshot, or you check your UPI app) unless you later integrate Razorpay/Cashfree UPI intents with webhook confirmation.

### Image Carousel
Swipe (mobile touch), click-arrow (desktop), and dot count are all standard carousel behaviors — a library like `embla-carousel` or `swiper` handles all three out of the box and is responsive.

### Discount Code & Loyalty Engine
With no backend database, this has to live as logic against your `products.json`/a small `codes.json`. Fine for a handful of static codes (e.g. `WELCOME10`); a real loyalty program (points, accounts) needs a real database — flag this as a Phase 2/3 item.

## 8. Things Worth Knowing Before You Build

- **JSON-as-database won't scale past a small catalog.** Fine for tens–low hundreds of products and no concurrent multi-admin editing. If you outgrow it, a lightweight hosted DB (Supabase/Postgres, or even Google Sheets as a poor-man's CMS) is a natural upgrade — same JSON contract, different source.
- **Google-image links can break or get rate-limited**, and hot-linking from Google Drive/Photos isn't guaranteed stable for a commercial storefront. Vercel Blob or Cloudinary (both have free tiers) are more reliable for production.
- **UPI QR without a payment gateway means manual payment confirmation.** Acceptable for a small brand starting out; budget time for reconciling orders by hand.
- **No real accounts/backend = no order history, no auth, no persistent cart across devices.** That's a reasonable MVP trade-off, just worth being explicit that it's a trade-off, not an oversight.
- **Cookie Consent / Privacy Policy**: even a simple storefront collecting name/address/phone for orders should have a real privacy policy, not just a placeholder — especially if you're targeting India (DPDP Act) or any EU visitors.
